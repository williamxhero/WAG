Verified public sources:

The reference does not define nullability for Pages/fields or guarantee behavior beyond what it specifies.
- [Tencent public document 130616](https://cloud.tencent.com/document/product/1806/130616) is “快速入门概述” (Quick Start Overview), not the SearchPro API reference.
- [Official Python SDK SearchPro models](https://github.com/TencentCloud/tencentcloud-sdk-python/blob/b9cdc2d401fdd148db6818e4e68d5922bf4580b9/tencentcloud/wsa/v20250508/models.py), pinned commit `b9cdc2d401fdd148db6818e4e68d5922bf4580b9`: `SearchProResponse.Pages` is `list of str`; the model's internal JSON keys and the `lite/standard/flagship` version values agree with the API reference. The SDK defines no nested Page model and documents no nullable guarantee.
- [Tencent pricing reference](https://cloud.tencent.com/document/product/1806/121798), verified for this task: lite/standard/flagship prices are RMB 14/20/26 per 1,000 calls. The current adapter already parses Pages as JSON strings. Its existing full-record validation collapses failures to `invalid_response`; in an offline synthetic reproduction, an allowlisted version remained in `posteriorVersion` even though a later record validation failed and no results were returned. This is an offline state-ordering defect, not evidence about the live canary's cause.

## Goal and defaults

Add an offline, safe, typed diagnostic for Tencent response processing that identifies the validation stage where processing failed, or `complete` only after the entire response batch validates, while preserving existing public success/failure behavior. Keep strict fail-closed parsing and all existing transport, signature, endpoint, request, response-size, tariff, quota, and dispatch behavior unchanged.

Default decisions and reasons:

- Diagnostic contract is a closed allowlist, projected into new objects at each boundary. Stage is one of `transport`, `response_json`, `response_envelope`, `version_validation`, `pages_array`, `page_json`, `record_validation`, or `complete`.
- Any diagnostic type fields use only `undefined`, `null`, `boolean`, `number`, `string`, `array`, or `object`. Any numeric fields are bounded non-negative safe-integer counts of actually observed items. Any boolean fields describe observed facts only. Optional fields vary by stage; unknown keys, values, free-form strings, nested objects, and unbounded numbers are discarded or rejected.
- `auth_success: true` is permitted only at stage `complete`, after the entire response passes JSON/envelope/no-Error/allowlisted-Version/Pages-array/every-page-JSON/every-record-normalization validation. At every intermediate stage it is `false` or unknown (`null`); version validation alone is not authentication success. Any failure leaves `posteriorVersion` null and returns no partial results. HTTP status alone, missing/unsupported version, an API error envelope, parse/record failure, or cache hit cannot mean authentication success.
- Do not put upstream text, response bodies, query, URL, title, headers, provider error codes/messages, exception/cause/stack, keys, request IDs, hashes, or secret/configuration presence into diagnostics or output. Do not log them.
- Keep diagnostics nested in Tencent `provider_attempts`; do not add a top-level MCP output field or modify unrelated providers' attempt shapes. Cache hits carry no fresh response diagnostic.
- Keep provider publication dates E4 claims only. Authentication/version/response diagnostics never promote E4 or satisfy page-level E1/E2 strict verification.
- Preserve reserve-before-send, the 3-cent Tencent reservation, quota accounting, cache behavior and no-refund-on-failure. Diagnostics never retry, refund, reprice, or authorize another request.
- Use the existing project Node requirement and no new dependency. The explicit local test runtime available for a later implementation pass is `C:/Users/will/AppData/Local/hermes/tools/node-26.7.0-win32-x64/node.exe`; do not upgrade the system Node runtime.

## Minimal implementation scope and rationale

The diagnostic must be produced where parsing evidence exists and must be revalidated at every boundary that serializes or exposes it. Therefore this is a deliberately small cross-module scope, not an architecture or routing redesign:

- `gateway/provider-adapters.mjs` and `gateway/provider-adapters.test.mjs`: add stage-specific safe diagnostics for Tencent transport/envelope/version/Pages/page-JSON/record outcomes; leave other providers unchanged; assign `posteriorVersion` only after the entire result set validates successfully (including valid empty Pages). Do not return partial results.
- `gateway/provider-contract.mjs` and `gateway/provider-contract.test.mjs`: define the shared diagnostic enum and strict projector so arbitrary transport/exception properties cannot cross the boundary.
- `gateway/provider-budget.mjs` and `gateway/provider-budget.test.mjs`: retain only the projected diagnostic on Tencent success/empty/failure attempts; preserve attempt status and committed reservations. Non-Tencent attempts are unchanged.
- `gateway/provider-routing.mjs` and `gateway/provider-routing.test.mjs`: forward only projected Tencent diagnostics into `provider_attempts`, preserving status and existing posterior-version gating. Do not infer a diagnostic on routing, budget, timeout, or cache-only outcomes.
- `scripts/provider-canary.mjs` and `gateway/provider-canary.test.mjs`: explicitly project the Tencent diagnostic into the existing safe canary JSON shape; never serialize the runtime attempt/error wholesale.
- NEW `gateway/provider-diagnostics.test.mjs`: table-driven end-to-end synthetic official-shaped response tests, including no-version, error-envelope, malformed/mixed Pages and full redaction sentinels.
- `gateway/provider-routing-boundary.test.mjs`: verify the existing MCP structured and text output preserves only the safe nested diagnostic and E4 remains non-verified.
- This SPEC document.

`gateway/provider-http-transport.mjs` and its tests are intentionally excluded: transport/authentication/signing/endpoint behavior is not to change. The adapter may map only its existing fixed safe transport `kind` values into an allowlisted diagnostic; unknown error properties are discarded. The adapter's blanket transport-error catch is an offline metadata-loss point to address only by preserving the existing safe failure class and adding fixed diagnostic fields, never by exposing the caught error. This does not identify the prior live failure cause.

No edits to provider configuration, costs/budgets, result evidence semantics, general logging, P0/#99/index/CI/packages, or production/deployment surfaces are included. No reopen of #96 and no close/update of #82 or any other issue.

## Acceptance criteria

All acceptance is offline and uses synthetic data only:

1. Test official-shaped SearchPro response parsing for `Pages: list[str]`, including empty Pages, valid nullable/empty optional record fields only where current normalizer permits them, malformed outer JSON, missing/null/wrong-typed Pages, invalid page JSON, object/array/null page JSON, mixed valid and malformed records, invalid record field types, and bounded result counts. Malformed/mixed responses fail closed with no partial results.
2. Missing/unknown/malformed Version, unsupported Version, malformed Error envelope, any Error envelope, invalid Pages/page JSON, or any invalid record cannot produce a posterior version or `auth_success: true`. Only the complete response passing every listed validation may set stage `complete`, `auth_success: true`, and posterior version together.
3. Verify fixed stage/enum/type/count/boolean schema and all allowlist boundaries. Inject sentinels for query, title, body, URL, headers, provider code/message, exception/cause/stack, key, request ID, hash, and secret/config-presence marker; serialize adapter, budget attempts, routing/MCP output, and canary output and assert none appear. No arbitrary upstream strings or unknown keys survive.
4. Verify diagnostics traverse adapter -> persistent budget attempt -> runtime router -> canary and existing MCP nested attempt output, only for Tencent. Other provider shapes and result/status behavior remain unchanged. Cache hits do not carry stale/freshly fabricated upstream diagnostics.
5. Verify a failed Tencent parse still consumes its already committed 3-cent reservation, dispatches once, does not retry/refund/reprice, and remains charged across ledger reopen. Diagnostics do not alter budget or fallback decisions.
6. Verify all API/provider dates remain E4 and strict page-only results exclude E4-only candidates even when authentication and version diagnostics indicate a valid envelope.
7. Run focused adapter, budget, routing, routing-boundary, canary, and diagnostic tests first using the explicit Node 26.7.0 binary; run relevant existing gateway regressions, syntax checks, and `git diff --check`. Record exact commands and results. No real provider request, credential read, SSH, production test/deployment, or ledger initialization.
